# API Conventions

**Version:** 1.0

**Status:** Active

---

# Purpose

This document defines the API conventions used throughout the CareerReady AI backend.

The objective is to ensure that every module follows a consistent RESTful design, making the API predictable for frontend developers, mobile applications, automated testing, and future integrations.

Unless there is a compelling technical reason, all modules must follow these conventions.

---

# General Principles

The API should be:

- RESTful
- Predictable
- Consistent
- Versioned
- Resource-oriented
- Easy to discover
- Easy to document

Business logic belongs in the service layer.

Controllers should remain thin.

Repositories should contain persistence logic only.

---

# Base URL

```
/api
```

Future versions will use:

```
/api/v1
```

Example

```
/api/v1/curriculum/frameworks
```

---

# Resource Naming

Resources use:

- plural nouns
- lowercase
- kebab-case when necessary

Examples

```
assessment-types

topics

concepts

frameworks

framework-steps

questions

assessments
```

Avoid verbs in URLs.

Good

```
GET /frameworks
```

Bad

```
GET /getFrameworks
```

---

# Standard CRUD Endpoints

Every curriculum resource should expose the following endpoints.

| Method | Endpoint | Description |
|---------|----------|-------------|
| POST | `/resource` | Create resource |
| GET | `/resource` | List resources |
| GET | `/resource/:id` | Retrieve resource |
| PATCH | `/resource/:id` | Update resource |
| DELETE | `/resource/:id` | Soft delete resource |
| PATCH | `/resource/:id/restore` | Restore soft-deleted resource |

Example

```
POST    /curriculum/frameworks

GET     /curriculum/frameworks

GET     /curriculum/frameworks/:id

PATCH   /curriculum/frameworks/:id

DELETE  /curriculum/frameworks/:id

PATCH   /curriculum/frameworks/:id/restore
```

---

# HTTP Status Codes

The API should use standard HTTP status codes.

| Status | Meaning |
|---------|----------|
| 200 | Success |
| 201 | Resource Created |
| 204 | No Content |
| 400 | Validation Error |
| 401 | Unauthorized |
| 403 | Forbidden |
| 404 | Resource Not Found |
| 409 | Conflict |
| 422 | Business Rule Validation |
| 500 | Internal Server Error |

---

# Request Validation

All request validation should use DTOs.

Validation is performed before entering the service layer.

Use:

- class-validator
- class-transformer

Controllers should not manually validate input.

---

# Response Format

Every endpoint should return a consistent response structure.

Example

```json
{
  "success": true,
  "data": {}
}
```

Errors should follow the global exception filter.

Example

```json
{
  "success": false,
  "statusCode": 404,
  "path": "/api/v1/curriculum/frameworks/123",
  "timestamp": "2026-07-25T10:15:00.000Z",
  "error": {
    "message": "Framework not found",
    "error": "Not Found",
    "statusCode": 404
  }
}
```

---

# Soft Delete

CareerReady AI uses soft deletes.

DELETE endpoints should never physically remove records.

Repositories should update:

```
deletedAt
```

instead.

---

# Restore Endpoint

Soft-deleted resources must expose:

```
PATCH /resource/:id/restore
```

Restoration should only succeed if the record exists.

---

# Pagination

Collections should eventually support pagination.

Recommended format

```
GET /frameworks?page=1&limit=20
```

Response

```json
{
  "data": [],
  "meta": {
    "page": 1,
    "limit": 20,
    "total": 100,
    "pages": 5
  }
}
```

Pagination will be implemented during an Optimization Sprint.

---

# Filtering

Filtering should use query parameters.

Example

```
GET /frameworks?status=PUBLISHED
```

Multiple filters

```
GET /frameworks?status=PUBLISHED&isCore=true
```

---

# Sorting

Sorting uses query parameters.

```
GET /frameworks?sort=name
```

Descending

```
GET /frameworks?sort=-createdAt
```

---

# Search

Search uses:

```
GET /frameworks?search=difference
```

The backend determines searchable fields.

---

# Relationships

Nested URLs should only be used where the relationship is explicit.

Example

```
GET /concepts/:id/frameworks
```

Avoid excessive nesting.

Bad

```
/assessment-types/1/topics/2/concepts/3/frameworks/4
```

Prefer filtering instead.

---

# Slugs

Resources that support human-readable URLs should expose:

```
slug
```

Slugs are:

- generated by the backend
- unique
- immutable unless the resource name changes

---

# Swagger

Every endpoint must include:

- ApiTags
- ApiOperation

Future additions should include:

- ApiResponse
- ApiParam
- ApiQuery

---

# Business Logic

Controllers must never:

- validate business rules
- query Prisma directly
- generate slugs
- perform authorization logic
- perform repository operations

Controllers delegate all work to services.

---

# Service Responsibilities

Services are responsible for:

- business validation
- uniqueness checks
- orchestration
- mapping DTOs
- repository coordination

---

# Repository Responsibilities

Repositories are responsible only for persistence.

Repositories should:

- contain Prisma queries
- define include/select graphs
- implement reusable query methods

Repositories should not contain business logic.

---

# Mapper Responsibilities

Mappers transform DTOs into Prisma models.

Responsibilities include:

- trimming strings
- generating slugs
- mapping nested objects
- preparing update payloads

Mappers should not access the database.

---

# Versioning

All public APIs should be versioned.

Example

```
/api/v1
```

Breaking changes require a new version.

---

# Documentation

Every new module must include:

- Swagger documentation
- Postman requests
- DTO validation
- API examples where appropriate

---

# Module Checklist

Every new module should follow this implementation order.

- Prisma Model
- Migration
- DTOs
- Mapper
- Repository
- Service
- Controller
- Module
- Swagger
- Manual Testing
- Automated Tests
- Documentation

---

# Future Improvements

The following enhancements are planned during Optimization Sprints.

- Shared validation helpers
- Shared response DTOs
- Pagination utilities
- Filtering utilities
- Sorting utilities
- Shared mapper utilities
- Shared repository helpers
- OpenAPI response documentation
- API versioning middleware

---

# Guiding Principle

The API should feel boring.

Developers should be able to predict how every endpoint behaves without reading its implementation.

Consistency is preferred over cleverness.
